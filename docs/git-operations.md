# Gitを正本にする運用

更新: 2026-09-30

## 結論

AI Work OSのコード、仕様、運用ルール、意思決定、検証要約、残課題はGitで管理する。GitHubのリポジトリを見れば、別のPCや別のAIでも現在地と次の作業を判断できる状態を維持する。

Google Driveは同期された作業場所と資料保管場所、PCはブラウザ操作やローカル実行の場所として使う。どのPCで作業しても、共有すべき変更はコミットしてGitHubへ反映する。

## 正本の優先順位

1. GitHub `main`: 共有可能なコード・仕様・運用状態。
2. Google Drive `WorkOS/02_プロジェクト/workspace/ai-work-os`: 編集用チェックアウト。
3. Vercel本番: デプロイ済み実装の確認先。
4. PC固有設定: 秘密情報、ログイン状態、キャッシュ、依存パッケージ。

Cドライブの旧チェックアウトは参照用。新しい正本として更新しない。内容照合が終わるまで削除しない。

## Gitに入れるもの

- アプリのコードとテスト
- PRD、設計、運用手順
- 現在できること、未完了、ブロッカー
- 自動化の意図、頻度、完了条件
- 実行結果の要約、根拠となる外部ID、検証日
- 障害記録と再発防止策
- スキルの編集正本。ただし汎用スキルは対応する専用リポジトリがある場合はそちらを優先

## Gitに入れないもの

- APIキー、パスワード、Cookie、OAuthトークン、`.env*`
- ブラウザプロファイルやログインセッション
- `node_modules`、ビルド成果物、キャッシュ
- 会員の自己紹介全文、不要な個人情報、DM全文
- 大容量の一時ファイル

秘密値が必要な機能は、必要な環境変数名、取得方法、権限範囲、未設定時の停止動作だけを文書化する。

## 変更の完了条件

1. 実装または文書を更新する。
2. 関連するテスト、lint、buildを必要な範囲で実行する。
3. [current-state.md](current-state.md) の状態または残課題を更新する。
4. 外部動作は外部側で読み戻し、結果を運用履歴へ記録する。
5. `git status`で意図しないファイルや秘密情報がないことを確認する。
6. 内容が分かるメッセージでコミットし、`main`へpushする。
7. GitHub上のコミットと本番が一致するか、デプロイ対象の場合は確認する。

## コミットの単位

- 目的が一つになる大きさにする。
- 「何をしたか」より「なぜ必要か」が分かるメッセージにする。
- 監査だけのコミットと実装コミットを区別する。
- 未検証を検証済みと書かない。
- 外部送信、公開、削除などの事実は、外部IDまたは読み戻し結果と一緒に残す。

## 日次運用記録

RIALAの無送信テストは `operations/riala-test-runs/` に個人情報を抑えた要約を残す。詳細な会員情報が必要な一時調査はGit外で扱い、Gitには件数、判定、重複確認、ブロッカー、根拠となる公開IDだけを記録する。
