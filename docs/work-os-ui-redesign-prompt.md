# AI Work OS UI/UX 再設計・実装プロンプト

あなたは、プロダクト戦略、情報設計、インタラクション設計、アクセシビリティ、フロントエンド実装を一人で担当できるシニアプロダクトデザイナー兼シニアエンジニアです。

対象は、人生目標、営業代行、RIALA運営、日々のタスク、AIの実行状況、PDCAを一つにつなぐ個人専用の **AI Work OS** です。見た目のリニューアル案だけを出すのではなく、既存コードと実データを調査し、設計、実装、レスポンシブ確認、操作テスト、修正まで完了してください。

## 1. このプロダクトが解決すること

ユーザーは複数の仕事と人生目標を並行しており、タスク量が多い。必要なのは「管理するための管理画面」ではなく、アプリを開いた瞬間に次の一歩が分かり、その場で実行し、成果と振り返りが目標へつながる体験です。

中心となる流れは次の通りです。

1. 目標と現在地を確認する。
2. AIが目標との差から必要な仕事を洗い出す。
3. 今日やる一件を決める。
4. 人またはAIが実行する。
5. 外部結果と実績時間を保存する。
6. PDCAで次の一手を決める。

管理項目を増やすほど良いわけではありません。ユーザーの判断回数と探す時間を減らし、実行までの距離を短くしてください。

このアプリの価値は効率だけではありません。開いた人が「遅れている」「またできていない」と責められるのではなく、頭の中の混乱が静まり、「これなら一つ進められそう」と感じられることを同じくらい重要な成果とします。ダッシュボードではなく、考えることを一時的に預けられる信頼できる伴走者として設計してください。

## 2. 対象ユーザー

- 忙しく、複数領域のタスクを抱えている一人の事業運営者。
- 長い説明、細かい表、同じ意味の数字が並ぶ画面を読む余裕がない。
- PCとスマートフォンの両方を使う。
- かわいさ、触り心地、立体感、温度のある言葉を好む。
- AIが作ったような大げさな見出し、抽象的なコピー、紫グラデーションの多用、意味のない光彩、絵文字の乱用を好まない。
- 数字や完了を捏造せず、「未確認」「情報待ち」「実行中」「成果確認待ち」を正確に区別したい。

## 3. 感情体験の目標

各画面を美しく整えるだけでなく、利用前後の感情が次のように変わる体験を設計してください。

- 開く前の「やることが多くて見たくない」を、開いた後の「今日はこれだけ見ればいい」に変える。
- 「遅れている、できていない」を、「今から選べる次の一歩がある」に変える。
- 「全部自分で覚えておかないと不安」を、「ここに預けておけば大丈夫」に変える。
- 「AIに管理されている」を、「自分の意志をAIが支えてくれている」に変える。
- 完了時は派手に祝うのではなく、「少し前に進んだ」と実感できる静かな達成感をつくる。

デザイン判断では常に「この表示は不安を減らすか」「次の行動を選びやすくするか」「自分を責める表現になっていないか」を確認してください。

### 感情に合わせた画面の役割

- TODAYは司令室ではなく、朝に開く落ち着いた机。今やる一件を中央に置き、残り全部を一度に背負わせない。
- TASKSは大量の仕事を見せる倉庫ではなく、必要なものをすぐ取り出せる引き出し。件数の多さで圧迫しない。
- GOALSは達成を迫る成績表ではなく、迷った時に方向を思い出す地図。人生の理由と今日の行動のつながりが見える。
- PDCAは反省会ではなく、経験を次へ生かす短い対話。「できなかった理由」より「次はどう軽くするか」を先に扱う。
- AI実行画面は機械の監視盤ではなく、仕事を安心して任せられる受付。何を預け、どこまで進み、何を確認すればよいかが分かる。

### 温度と愛着

- 季節、時間帯、連続利用日数を誇張せず、ごく小さな変化として背景や挨拶に反映してよい。
- ユーザー自身の言葉、目標の理由、過去にできたことを必要な場面で短く返し、「自分のための場所」と感じられるようにする。
- かわいさは絵文字や装飾の量ではなく、丸み、余白、触れた時の反応、丁寧な日本語、小さなイラストで表現する。
- 立体感は触りたくなる手がかりとして使う。押せない装飾をボタンのように見せない。
- 毎回同じ励ましを出さない。褒めすぎず、行動の事実を短く認める。

感情を操作するダークパターン、罪悪感を生む連続記録、赤い警告の乱用、焦らせるカウントダウン、根拠のない称賛は禁止します。

## 4. 最優先のユーザー行動

画面ごとの最優先行動は一つに絞ります。

- TODAY: 今やる一件を開始する。
- TASKS: 必要なタスクを3秒以内に見つけ、開く。
- GOALS: 目標の現在地と、次に効く行動を理解する。
- PDCA: 実績と詰まりを確認し、次の一手を一件決める。
- AREA: 営業代行・RIALA・GENESISそれぞれの成果、未対応、次の実行を確認する。

各画面で主ボタンは原則一つです。副操作は視覚的に弱め、詳細操作は必要になった時だけ展開してください。

## 5. 最初に行う監査

コードを変更する前に、現在の画面を390px、768px、1440pxで確認してください。TODAY、TASKS、GOALS、PDCA、営業代行、RIALA、タスク詳細を対象に、次を記録してください。

- 画面を開いて3秒以内に目的が分かるか。
- 最優先行動が一つに見えるか。
- 同じ情報、説明、ボタンが重複していないか。
- 重要な情報がスクロール下部に埋もれていないか。
- 数字の意味と取得元が分かるか。
- 文字が小さすぎないか。最低14px、本文は原則16px以上。
- タップ領域が44px以上か。
- モーダル、キーボード操作、フォーカス復帰が正しいか。
- 横スクロール、切れ、過度な改行がないか。
- 参考データを実績のように見せていないか。
- 開いた瞬間に焦り、罪悪感、圧迫感を強めていないか。
- 一画面に「今すぐ対応すべきもの」が複数競合していないか。
- 言葉が命令、評価、説教に聞こえないか。

監査結果を「問題 / 操作への影響 / 感情への影響 / 修正 / 検証方法」の表にし、影響が大きい順に実装してください。監査文書だけで終了しないでください。

## 6. 情報設計

### TODAY

ファーストビューには次だけを置きます。

- 日付と短い挨拶。
- 今やる一件。タイトル、領域、完了条件、見積り、開始ボタン。
- 次の予定を最大2件。
- 追加ボタン。

期限超過、情報待ち、Calendarとの差、持ち越し、詳細計画は二次領域へ置きます。未設定や未確認が多い時も、警告を大量に並べず、直すべき一件と件数を示してください。

### TASKS

- 検索、状態、領域を一列または一つのフィルタシートにまとめる。
- 初期表示は未完了。完了・アーカイブは明示的に切り替えた時だけ表示。
- タスクカードはタイトル、状態、領域、実行日または期限、見積りだけを表示。
- カード全体を開けるようにし、編集ボタンを乱立させない。
- AI担当は「受付待ち」「実行中」「成果確認待ち」「確認済み」を正確に表示する。

### GOALS

- 人生、仕事、期間目標の関係を、巨大なツリーではなく段階的に読める構成にする。
- カードには目標名、期限、現在地の根拠、次に効く行動を表示する。
- タスク完了数を目標達成率として扱わない。
- 成果の根拠がなければ「未確認」と表示する。

### PDCA

- 上段は「できたこと」「詰まっていること」「次の一手」の3要素。
- 実績時間は測定済みのみ集計し、未入力を0分にしない。
- グラフは意思決定に使える場合だけ表示する。装飾目的のグラフは禁止。
- 行動ログの羅列より、今週の変化と次に変えることを優先する。

### タスク詳細

最初に見える順序を固定します。

1. タイトルと状態。
2. 何をするか。
3. ここまでできたら完了。
4. 作業日時と実績。
5. 主操作。
6. 関連目標。
7. AIの成果物と根拠。
8. 履歴・詳細設定。

## 7. ビジュアル方針

「柔らかく、愛着があり、毎日開きたくなる仕事道具」にしてください。子ども向け、ゲーム画面、AIチャット画面にはしません。

- ベース: 温かいオフホワイトまたはごく薄いニュートラルグレー。
- 文字: 黒に近いチャコール。本文コントラストはWCAG AAを満たす。
- ブランド色: 落ち着いた一色。主ボタン、現在地、選択状態だけに使う。
- 状態色: 成功、注意、危険、情報待ちに限定し、面積を小さくする。
- 8pxグリッドを基本とし、4pxはアイコン内部などの微調整だけに使う。
- 角丸はカード16px、ボタン12pxなど役割ごとに統一する。
- 影は2段階まで。カードを浮かせすぎない。
- 立体感は、面の重なり、1px境界、押下時の1〜2px移動、控えめなハイライトで表現する。
- 3DオブジェクトはヘッダーまたはEmpty Stateに限定し、情報を押し下げない。低性能端末と`prefers-reduced-motion`に配慮する。
- アイコンは同一セット・同一線幅で統一する。
- 絵文字をナビゲーションアイコンとして使わない。
- 大文字英語の飾り見出しは原則削除する。日本語だけで意味が伝わるようにする。
- グラデーション、ガラス表現、ネオン、光彩を同時に使わない。

参考にするのは特定サービスの表面コピーではなく、Linearの速度と情報密度、Thingsの明快な階層、Airbnbの安心できる余白、Duolingoの触り心地です。AI Work OS固有の人格に統合してください。

## 8. コピーのルール

- 人が普段使う短い日本語にする。
- 「最適化」「インサイト」「エンパワー」「次世代」など抽象語を避ける。
- 状態と次にできることを具体的に書く。
- 成功メッセージを大げさにしない。
- 「未達」「遅延」「消化」など人を採点する言葉を主見出しにしない。
- 問題を示す時は、責める文章ではなく、事実と今できる行動を並べる。
- AIが実行していないことを「実行中」と表示しない。受付済みは受付済みと書く。
- 保存できなかった時は、消えたか、端末に残っているか、再試行できるかを伝える。

例:

- 悪い: 「今日のミッションを最適化しましょう」
- 良い: 「まず、この1件から」
- 悪い: 「AIが魔法のように実行しています」
- 良い: 「実行担当が受け取るのを待っています」
- 悪い: 「期限超過が5件あります。すぐ対応してください」
- 良い: 「予定を過ぎたものが5件あります。今日は1件だけ決め直しましょう」
- 悪い: 「今日の達成率は20%です」
- 良い: 「今日は1件進みました。次にするなら、この1件です」

## 9. 状態設計

各画面で次を必ず設計・実装してください。

- 読み込み中: レイアウトが跳ねないスケルトン。
- データなし: 理由と最初の一歩が一つだけ分かるEmpty State。
- 検索0件: 条件を戻す導線。
- 未接続: 参考表示と実データを明確に区別し、接続導線を一つ表示。
- 保存中 / 保存済み / 端末に未送信 / 競合 / 保存失敗。
- 情報待ち / 期限超過 / AI受付待ち / AI実行中 / 成果確認待ち。
- 権限不足: 実行可能に見せない。

Empty Stateに意味のないダミータスクや架空の達成数を入れないでください。

## 10. インタラクションとアクセシビリティ

- マウス、タッチ、キーボードですべての主操作を行えること。
- フォーカス表示を消さない。
- モーダルはTabを閉じ込め、Escapeで閉じ、閉じた後は開いた要素へフォーカスを戻す。
- 色だけで状態を伝えない。
- アニメーションは150〜240msを基本とし、待ち時間を増やさない。
- ドラッグ操作を採用する場合は、同じ操作をボタンでも実行可能にする。
- 破壊的操作は確認する。日程変更、開始、中断は必要以上に確認を挟まない。

## 11. 実装上の制約

- 既存のNext.js、React、Tailwind構成を尊重する。
- 実データ、中央保存、履歴、既存APIを壊さない。
- 既存の詳細機能を削除せず、主画面から適切に段階開示する。
- 表示だけの偽ボタン、固定の成功値、架空のグラフを作らない。
- 新しい依存関係は、既存CSSとReactで実現できない明確な理由がある場合だけ追加する。
- 巨大な1ファイルへ実装を集中させず、再利用できる責務単位へ分ける。
- モバイルを縮小版デスクトップにしない。390pxで最優先行動が最初に見える構成へ組み替える。

## 12. 完了条件

次の全項目を満たすまで完了と報告しないでください。

1. TODAY、TASKS、GOALS、PDCA、タスク詳細を実装済み。
2. 営業代行とRIALAの主要画面も同じ設計体系へ統一済み。
3. 390px、768px、1440pxで横はみ出しがない。
4. 各画面の目的と主操作を3秒以内に説明できる。
5. 主操作までのクリック数が従来以下。
6. 文字サイズ、コントラスト、タップ領域、キーボード操作を確認済み。
7. Empty、Loading、Error、未接続、保存競合を確認済み。
8. タスク開始→中断→再開→完了→再読み込み→PDCA反映を実データと隔離テストで確認済み。
9. 日程変更、目標編集、AI成果物確認を保存後の再読み込みまで確認済み。
10. 既存の自動テスト、lint、production buildが成功。
11. Before / Afterのスクリーンショットと、改善した判断時間・操作数・読みやすさを報告。
12. 未接続の外部データや未検証の実運用を、完成扱いにしていない。
13. 5秒テストで「今やること」「後でよいこと」「AIに任せていること」を説明できる。
14. ユーザビリティ確認で、操作時間だけでなく「圧迫感」「安心感」「また開きたいか」を5段階で確認し、圧迫感が下がり安心感と再利用意向が上がっている。
15. 期限超過が多い状態、タスクが100件以上ある状態、何も完了できなかった日でも、責められているように見えず、次の一歩を一つ選べる。

## 13. 出力と進め方

最初に長い提案書だけを返さないでください。以下の順で進めてください。

1. 現在のコード、実画面、データ状態を確認する。
2. 重大な問題を最大10件に絞って提示する。
3. 画面ごとの情報階層と共通デザイントークンを決める。
4. 影響の大きい画面から実装する。
5. ブラウザで操作し、問題があればその場で直す。
6. テスト、lint、buildを実行する。
7. 変更した内容、確認できたこと、まだできていないことを事実ベースで報告する。

ユーザーへ実装途中の選択を何度も質問せず、既存の好みと上記原則から合理的に判断してください。セキュリティ、外部送信、本番公開など取り消しにくい操作以外は、監査だけで止まらず実装と検証まで進めてください。
